# Coach App — приложение для тренера

Учебный full-stack проект курса «Fullstack» (1 семестр). Веб-приложение помогает тренеру вести
спортсменов: хранить список группы, составлять планы тренировок по неделям, следить за
календарём занятий и отмечать посещения. Также в карточке спортсмена ведётся учёт травм и питания.

**Стек:** React + TypeScript (frontend), Python + FastAPI (backend), PostgreSQL + SQLAlchemy (БД).
Библиотека UI-компонентов — [Mantine](https://mantine.dev): в ней есть готовые формы, таблицы,
вкладки и модальные окна, она типизирована под TypeScript и даёт единое оформление из коробки.

## Пользовательские сценарии

1. **Тренер смотрит список спортсменов** — ищет по имени, открывает карточку спортсмена.
2. **Тренер открывает карточку спортсмена** — видит общую информацию, травмы, питание и посещаемость.
3. **Тренер планирует неделю** — открывает план тренировок, переключается между неделями.
4. **Тренер отмечает посещения** — выбирает занятие в календаре и отмечает, кто присутствовал.

Простые отчёты (посещаемость, травмы, питание) запланированы на следующие этапы проекта.

Отметки посещений во frontend пока хранятся в состоянии компонента и сбрасываются при перезагрузке
страницы. Backend для их сохранения готов (ЛР2), frontend подключится к нему в ЛР5.

## Запуск frontend

Требуется Node.js 20+.

```bash
cd frontend
npm install
npm run dev
```

Приложение откроется на http://localhost:5173. На этом этапе используются демонстрационные данные,
backend не нужен.

## Запуск backend

Требуется Python 3.12+ и PostgreSQL 16. Команды — для PowerShell.

**1. База данных.** Проще всего запустить PostgreSQL в Docker и создать пустую базу `coach`:

```powershell
docker run --name fs-postgres -e POSTGRES_PASSWORD=<пароль> -p 5432:5432 -v fs-pgdata:/var/lib/postgresql/data -d postgres:16
docker exec -it fs-postgres psql -U postgres -c "CREATE DATABASE coach;"
```

После перезагрузки компьютера контейнер запускается командой `docker start fs-postgres`.
Пароль лучше составить только из латинских букв и цифр: символы `@`, `:` и `/` ломают строку подключения.

**2. Окружение и настройки** (из папки `backend`):

```powershell
cd backend
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
copy .env.example .env      # затем вписать в .env свой пароль от PostgreSQL
```

**3. Таблицы и начальные данные** (необязательно):

```powershell
python -m app.seed
```

Команда создаёт таблицы и заполняет пустую базу демонстрационными данными: 8 спортсменов из
frontend, расписание на 5 недель (3 прошедшие, текущая и следующая) и отметки посещений
прошедших занятий. Если в базе уже есть спортсмены, данные не добавляются.

**4. Запуск сервера:**

```powershell
uvicorn app.main:app --reload
```

Сервер откроется на http://127.0.0.1:8000, интерактивная документация API — http://127.0.0.1:8000/docs.
Проверка, что сервер жив: `GET /health` возвращает `{"status": "ok"}`.

Таблицы создаются автоматически при каждом старте сервера (`Base.metadata.create_all`), поэтому
шаг 3 можно пропустить. Уже существующие таблицы при этом не изменяются: если модель поменялась,
таблицу нужно удалить, и при следующем запуске она создастся заново.

Настройки читаются из `backend/.env` (образец без секретов — `backend/.env.example`):

| Переменная | Назначение |
|---|---|
| `APP_NAME` | название API в документации `/docs` |
| `DEBUG` | режим отладки FastAPI (`true` / `false`) |
| `DATABASE_URL` | строка подключения к PostgreSQL; обязательна — без неё сервер не стартует |
| `CORS_ORIGINS` | адреса frontend, которым разрешены запросы к API, в виде JSON-списка; по умолчанию `http://localhost:5173` и `http://127.0.0.1:5173` |

## Модель данных

```
athletes 1 ──< attendance >── 1 training_sessions
```

| Таблица | Поля | Ограничения |
|---|---|---|
| `athletes` — спортсмены | `id`, `name`, `age`, `group`, `status`, `phone`, `goal` | PK `id`; `status` ∈ `active`, `injured`, `rest` |
| `training_sessions` — занятия | `id`, `date`, `time`, `title`, `group`, `kind` | PK `id`; `kind` ∈ `strength`, `cardio`, `technique`, `recovery` |
| `attendance` — посещения | `id`, `athlete_id`, `session_id`, `present` | PK `id`; FK на `athletes` и `training_sessions` с `ON DELETE CASCADE`; пара (`athlete_id`, `session_id`) уникальна |

- `attendance` связывает спортсменов и занятия по схеме «многие-ко-многим» и хранит отметку
  `present`. Спортсмена нельзя отметить на одном занятии дважды и нельзя отметить на занятии
  чужой группы.
- При удалении спортсмена или занятия их отметки посещений удаляются вместе с ними.
- Процент посещаемости (`attendance_rate` в ответах `/athletes`) не хранится: он вычисляется
  подзапросом к `attendance` в том же SQL-запросе, что и сам спортсмен. Если отметок нет — `null`.
- Ограничения на статус и тип занятия проверяются и в API, и в самой БД (CHECK).
- Группа хранится строкой в `athletes.group` и `training_sessions.group`. Отдельные таблицы для
  групп, травм и питания в ЛР2 не делались: основные сценарии тренера (список спортсменов,
  расписание, отметка посещений) закрываются тремя таблицами выше.

## API

| Метод | Путь | Назначение | Успех | Ошибки |
|---|---|---|---|---|
| GET | `/health` | проверка, что сервер отвечает | 200 | — |
| GET | `/athletes?group=` | список спортсменов по имени с процентом посещаемости, фильтр по группе необязателен | 200 | 422 |
| GET | `/athletes/{id}` | спортсмен по id | 200 | 404, 422 |
| POST | `/athletes` | добавить спортсмена | 201 | 422 |
| PATCH | `/athletes/{id}` | изменить переданные поля | 200 | 404, 422 |
| DELETE | `/athletes/{id}` | удалить спортсмена вместе с его посещениями | 204 | 404 |
| GET | `/sessions?date_from=&date_to=&group=` | занятия по дате и времени; фильтры необязательны | 200 | 400, 422 |
| GET | `/sessions/{id}` | занятие по id | 200 | 404, 422 |
| POST | `/sessions` | добавить занятие | 201 | 422 |
| PATCH | `/sessions/{id}` | изменить переданные поля | 200 | 404, 422 |
| DELETE | `/sessions/{id}` | удалить занятие вместе с отметками посещений | 204 | 404 |
| GET | `/attendance?session_id=&athlete_id=` | отметки посещений; фильтры необязательны | 200 | 422 |
| GET | `/attendance/{id}` | отметка по id | 200 | 404, 422 |
| POST | `/attendance` | отметить спортсмена на занятии | 201 | 400, 404, 409, 422 |
| PATCH | `/attendance/{id}` | изменить отметку `present` | 200 | 404, 422 |
| DELETE | `/attendance/{id}` | удалить отметку | 204 | 404 |

Полное описание запросов и ответов — на http://127.0.0.1:8000/docs.

### Ошибки

| Статус | Когда | Пример сообщения |
|---|---|---|
| `400` | нарушено правило предметной области | «Спортсмен не состоит в группе этого занятия», «Дата начала периода позже даты окончания» |
| `404` | запись не найдена | «Спортсмен не найден», «Занятие не найдено», «Отметка посещения не найдена» |
| `409` | конфликт с существующими данными | «Посещение этого спортсмена на занятии уже отмечено» |
| `422` | данные не прошли проверку | «Обязательное поле», «Должно быть не меньше 5», «Должно быть датой в формате ГГГГ-ММ-ДД» |

Ошибки `400`, `404` и `409` возвращаются как `{"detail": "сообщение"}`. Ошибка `422` перечисляет
все неверные поля сразу:

```json
{
  "detail": [
    {"field": "name", "message": "Минимальная длина — 1 симв.", "type": "string_too_short", "loc": ["body", "name"]},
    {"field": "age", "message": "Должно быть не меньше 5", "type": "greater_than_equal", "loc": ["body", "age"]}
  ]
}
```

`field` и `message` предназначены для показа пользователю, `type` и `loc` — для программной обработки.

Ошибки `400`, `404` и `409` возникают в сервисном слое (`app/services/errors.py`) и превращаются
в HTTP-ответы общими обработчиками (`app/api/errors.py`); там же сообщения `422` переводятся на русский.
Повторная отметка ловится уникальным ограничением в БД: даже при одновременных запросах
второй получит `409`, а не дубль.

### Проверка

Все сценарии проверены вручную через `/docs` и запросами к API на чистой базе:

- создание, чтение, изменение и удаление спортсменов, занятий и отметок посещений;
- фильтры по группе, периоду дат, занятию и спортсмену;
- ответы `400`, `404`, `409` и `422` с русскими сообщениями;
- каскадное удаление отметок при удалении спортсмена или занятия;
- ограничения БД (уникальность отметки, CHECK для статуса и типа, внешние ключи) — прямыми
  запросами в `psql`, в обход API;
- процент посещаемости после добавления и изменения отметок;
- повторный запуск `python -m app.seed` не дублирует данные.

## Структура репозитория

```
frontend/
  src/
    components/   переиспользуемые компоненты (каркас страницы, навигация)
    pages/        экраны приложения, по одному файлу на маршрут
    data/         демонстрационные данные и их типы
    lib/          вспомогательные функции (работа с датами)
backend/
  app/
    main.py       создание приложения FastAPI, CORS, обработчики ошибок, роутеры
    seed.py       заполнение базы начальными данными (python -m app.seed)
    core/         конфигурация (настройки из .env)
    db/           подключение к PostgreSQL, сессии, базовый класс моделей
    models/       модели SQLAlchemy (таблицы)
    schemas/      схемы Pydantic: проверка запросов и форма ответов
    services/     операции с данными
    api/errors.py обработчики ошибок: 400 / 404 / 409 и русские сообщения 422
    api/routes/   роутеры API, по одному файлу на ресурс
  requirements.txt
  .env.example    образец настроек без секретов
docs/
  screenshots/    скриншоты всех экранов
```

Структура frontend опирается на назначение модуля: `pages` — экраны, `components` — общие
элементы интерфейса, `data` — данные предметной области, `lib` — утилиты. Более подробное
деление (в сторону Feature-Sliced Design) запланировано на ЛР3, когда появятся
пользовательские действия и работа с API.

## История изменений интерфейса

- Календарь на узких экранах получил горизонтальную прокрутку: семь колонок не помещаются
  в ширину телефона, а перенос дней на несколько строк ломает привычную сетку недели.
- Пустые состояния (пустой поиск, неделя без тренировок) вынесены в общий компонент
  `EmptyState`, чтобы формулировки и отступы совпадали на всех экранах.
- Название месяца в календаре собирается вручную вместо CSS-капитализации: иначе
  `toLocaleDateString` добавлял сокращение «г.», и оно поднималось в «Г.».
